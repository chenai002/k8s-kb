# Agent Sandbox（给 Agent 一个秒开、用完就扔的执行环境）

> ⚠️ **待核实**：本文基于截止 2026 年中的公开设计讨论整理，**当前无法联网核对仓库状态与 API 细节**。Agent Sandbox 是 Kubernetes SIG 下较新的项目，CRD 名称、API 版本、是否已进入 alpha/beta 可能已变化，请以 `kubernetes-sigs` 官方仓库为准。

| 项 | 内容 |
| --- | --- |
| 方向 | A. 在 K8s 上跑 Agent |
| 难度 | ⭐⭐⭐ |
| 是什么 | 一个为 AI Agent 提供「快速、隔离、批量」沙箱的 K8s 扩展 |
| 一句话 | 把「起一个安全的小房间」这件事做到亚秒级 |
| 关键分层 | 上层编排（本篇） + 底层隔离（[gvisor-kata.md](./gvisor-kata.md)） |

## 一、先看一个场景

假设你做了一个「数据分析 Agent」。用户问：「帮我分析这份 CSV，画出销售额趋势图」。

Agent 会：
1. 写一段 Python 代码；
2. **执行它**；
3. 看报错，改代码，再执行；
4. 反复几轮，直到出图。

这个「执行代码」的步骤，就是沙箱要干的活。

再看一个更真实的场景：一个「代码审查 Agent」同时处理 500 个 PR，每个 PR 都要起一个环境跑测试、跑 lint。**500 个沙箱，建立后几分钟就销毁。**

现在问题来了：**用 Pod 做沙箱行不行？**

---

## 二、为什么 Pod 不够用

### 2.1 起一个 Pod 有多慢

```
kubectl run sandbox → apiserver 写入 etcd
                    → scheduler 选节点
                    → kubelet 接管
                    → CNI 分配 IP、配网络
                    → CSI 挂载卷（如果有）
                    → 拉镜像（如果没缓存）
                    → 起容器
```

冷启动 **1–5 秒**很常见，拉镜像时更久。对「Agent 改一行代码就再跑一次」的场景，这个延迟不可接受。

### 2.2 数量压力

500 个沙箱 = 500 个 Pod。每个 Pod 都在 etcd 里有完整对象、都有 kubelet 与 CNI 的完整生命周期。

- 频繁创建/删除会给 **apiserver 与 etcd 带来写入压力**（etcd 是最脆弱的组件）。
- Pod 的「终止」链路很长（finalizer、优雅退出、卷卸载），堆积 `Terminating` 很常见。
- Scheduler 在高频 Pod 创建下会成为瓶颈。

### 2.3 语义不匹配

Pod 是为「长期运行的服务」设计的：有就绪探针、有 Service 发现、有重启策略。
但沙箱的语义是：**「给我一个能跑东西的盒子，用完就扔，不要重试，不要服务发现」**。

用 Pod 表达这个语义，要绕很多弯（比如永远 `restartPolicy: Never`、禁用探针、独占节点）。

**所以社区提出了一个专门的抽象：Sandbox。**

---

## 三、Agent Sandbox 做了什么

用一句话概括：**引入一个比 Pod 更轻、更快的「沙箱」资源，配合预热池实现亚秒级启动。**

它大致提供三类能力：

1. **Sandbox / SandboxTemplate 资源**：声明「我要一个什么样的沙箱」。
2. **预热池（warm pool）**：提前创建一批空闲沙箱，请求来了直接分配。
3. **生命周期与隔离**：自动回收、强隔离运行时（gVisor/Kata）。

> ⚠️ 具体 CRD 名称（可能叫 `Sandbox`、`SandboxTemplate`、`SandboxClaim` 等）与 API 字段以官方设计文档为准。

---

## 四、实现原理（拆开看）

### 4.1 核心思路：把「创建」和「启动」分开

普通 Pod 的问题是**创建和启动耦合在一起**：

```
请求 → 创建 Pod（慢）→ 启动容器 → 可用
```

Agent Sandbox 的思路是**预先把「创建」做完**：

```
空闲时：沙箱池（已经存在，随时可用）
                    │
请求 → 从池里领一个（快）→ 重置状态 → 注入代码 → 运行
                    │
          用完 → 销毁 / 归还 / 快照
```

这样，**Agent 等待的时间从「秒级」降到「毫秒级」**。

### 4.2 三种加速手段

| 手段 | 原理 | 效果 |
| --- | --- | --- |
| **预热池** | 事先创建好 N 个空沙箱 | 启动 = 分配，最快 |
| **快照恢复** | 把「加载好依赖的环境」做成快照，用时恢复 | 秒级 → 亚秒级 |
| **简化启动路径** | 跳过调度、CNI、CSI 等步骤 | 减少控制面交互 |

### 4.3 架构示意

```
┌────────────────────────────────────────────────────────────┐
│ 控制面插件 / Controller                                     │
│  · watch Sandbox / SandboxTemplate / Pool 资源              │
│  · 维护预热池大小                                          │
│  · 处理「申请 → 分配 → 回收」                               │
└───────────────┬────────────────────────────────────────────┘
                │
                ▼
┌────────────────────────────────────────────────────────────┐
│ 沙箱池（可能以 Pod / 专用运行时实例形式存在）                 │
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐              │
│  │ 空闲    │ │ 空闲    │ │ 使用中  │ │ 使用中  │  ...        │
│  └────────┘ └────────┘ └────────┘ └────────┘              │
│       ▲          ▲                                         │
│       └──────────┴── 分配给 Agent 的请求                    │
└────────────────────────────────────────────────────────────┘
                │
                ▼
┌────────────────────────────────────────────────────────────┐
│ 隔离层：RuntimeClass → gVisor (runsc) / Kata               │
│  · Agent 的代码在这里执行，宿主内核碰不到                    │
└────────────────────────────────────────────────────────────┘
```

### 4.4 一次请求的生命周期

```
① Agent 需要执行代码
   POST /sandboxes（或创建 SandboxClaim 资源）
       │
② 控制器从池中取一个空闲沙箱
   · 如果池空 → 立即创建（慢路径，但很少发生）
       │
③ 注入代码与依赖（挂载 ConfigMap / 传参 / 执行入口命令）
       │
④ 执行 → 收集 stdout / 文件产物 / 退出码
       │
⑤ 清理与回收
   · 重置文件系统（或用快照重建）
   · 归还池中，或直接销毁
```

**关键设计问题：状态怎么清？**
- **销毁重建**：最干净，但慢。
- **重置文件系统**：用 overlay/快照，把写入层丢弃，快。
- **隔离到只读根 + 临时卷**：用完直接丢临时卷。

这也是为什么「快照恢复」是核心技术 —— 它能同时解决「快」和「干净」。

### 4.5 与 K8s API 的关系

这里有个设计权衡：

| 做法 | 优点 | 缺点 |
| --- | --- | --- |
| 每个沙箱一个 K8s 对象 | 可观测、可审计、能用 RBAC | 高频创建会压垮 etcd |
| 沙箱只在控制器内存中管理 | 极快 | 不透明、难以审计 |
| 混合（池用对象、实例用内部状态） | 平衡 | 实现复杂 |

社区的方向倾向于**混合**：池与模板是 K8s 对象，单个实例的生命周期由控制器在内部管理。

## 五、怎么用（概念示例）

> ⚠️ 以下 YAML 是**示意**，真实 API 可能完全不同，请以官方为准。

```yaml
# 1. 定义「沙箱长什么样」
apiVersion: agents.x-k8s.io/v1alpha1     # ⚠️ 猜测，以官方为准
kind: SandboxTemplate
metadata:
  name: python-data-science
spec:
  image: myregistry/python-ds:3.12
  runtimeClassName: gvisor               # 用 gVisor 隔离
  resources:
    requests: { cpu: 500m, memory: 1Gi }
    limits:   { cpu: 2,    memory: 4Gi }
  timeoutSeconds: 300
  networkPolicy: deny-egress              # 默认不允许外联
---
# 2. 申请一个沙箱
apiVersion: agents.x-k8s.io/v1alpha1
kind: Sandbox
metadata:
  name: job-1234
spec:
  templateRef:
    name: python-data-science
  command: ["python", "/work/analyze.py"]
```

**用户的观感**：`kubectl apply` 一个 Sandbox，几毫秒后 Pod（或沙箱实例）就 Ready 了。

## 六、什么时候该用它

| 场景 | 适合 | 原因 |
| --- | --- | --- |
| Agent 执行用户/模型生成的代码 | ✅ | 需要强隔离 + 快速创建 |
| 一次性数据处理任务 | ✅ | 短命、多、需要快 |
| 长期运行的服务 | ❌ | 用 Deployment 更合适 |
| 需要 GPU 的推理 | ❌ | 沙箱通常不直通 GPU；用 KServe |
| 有状态数据库 | ❌ | 生命周期与数据持久化冲突 |

## 七、有什么坑

### 7.1 还在早期

API 可能变，生产使用要评估。**如果现在就要上生产，更稳的做法是：**
- 自己用 `RuntimeClass`（gVisor）+ 一个简单的预热池 Deployment 实现；
- 或者用云厂商的沙箱服务（如各家的 Agent 沙箱 / Code Interpreter）。

### 7.2 池的容量规划

池太小 → 请求来时现建，慢；池太大 → 空跑占资源。

需要根据 QPS × 执行时长估算：
```
平均并发 = QPS × 平均执行时间
池大小 ≈ 平均并发 × (1 + 缓冲系数)
```

### 7.3 状态污染

如果沙箱是复用的（归还池），上一个任务的残留文件、环境变量可能影响下一个任务。必须做**彻底重置**（这也是为什么很多方案选择「用完就销毁」）。

### 7.4 网络出口

Agent 代码可能尝试访问外部网络（下载依赖、挖矿、数据外泄）。默认应该 **deny egress**，只放行必要的包仓库。

### 7.5 可观测性

沙箱数量巨大且短命，传统「按 Pod 监控」的方式不适用。需要：
- 聚合指标（创建数、等待时长、失败率）；
- 按任务 ID 关联日志。

### 7.6 与调度器的关系

如果沙箱用特殊运行时（gVisor/Kata），节点需要打好标签，并且要预留资源。用 `RuntimeClass.scheduling` 让调度器自动处理。

## 八、小白容易混淆的点

| 混淆 | 澄清 |
| --- | --- |
| **Agent Sandbox 是产品还是框架？** | 是 K8s 社区的**项目/抽象**，不是 SaaS 产品；具体实现依赖部署方 |
| **它和 gVisor 是竞争关系吗？** | 不是。Sandbox 是「怎么快速创建」，gVisor 是「创建出来的东西怎么隔离」，是上下游 |
| **它和 Pod 的区别？** | Pod 是通用运行单位；Sandbox 是「短命、隔空、可选池化」的专用单位 |
| **它和 FaaS（如 Knative）像吗？** | 有点像（都关注冷启动），但 FaaS 关注「处理请求」，Sandbox 关注「安全执行不可信代码」 |
| **是不是每个 Agent 都要一个沙箱？** | 不是。Agent 本身可以常驻，只有「执行代码」这一动作需要沙箱 |

## 九、面试会怎么问

**Q1：为什么 Agent 场景需要专门的沙箱抽象？**
因为需要「亚秒级创建 + 强隔离 + 高频生命周期」，Pod 的创建路径（调度、CNI、CSI）与生命周期管理（finalizer、优雅终止）成本太高。

**Q2：怎么做到亚秒级启动？**
预热池（提前创建）、快照恢复（跳过初始化）、简化启动路径（避开完整 Pod 生命周期）。

**Q3：隔离怎么实现？**
底层用 gVisor 或 Kata，通过 RuntimeClass 指定；网络默认拒绝，文件系统只读 + 临时卷。

**Q4：状态怎么保证不串？**
用完即销毁，或丢弃 overlay 写入层（快照重建），并使用只读根文件系统 + 临时卷。

**Q5：它和 Knative / KEDA 的关系？**
都涉及弹性，但目标不同：Knative 面向请求驱动的服务缩容到 0；Sandbox 面向不可信代码的安全执行与高频创建。
