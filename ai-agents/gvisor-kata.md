# gVisor 与 Kata Containers（怎么隔离 AI 生成的代码）

> ⚠️ **待核实**：本文原理部分相对稳定（属于操作系统与容器运行时基础），但具体版本、CRI 支持细节、与 K8s RuntimeClass 的配合方式请以官方文档为准。

| 项 | 内容 |
| --- | --- |
| 方向 | A / C. 运行 Agent 的底层隔离能力 |
| 难度 | ⭐⭐ |
| 是什么 | 两种「比普通容器更安全」的沙箱运行时 |
| 一句话 | 普通容器是「合租」，gVisor/Kata 是「独门独户」 |

---

## 一、为什么 AI Agent 需要它

Agent 的一个重要能力是 **执行代码**：写 Python 脚本算数据、跑 SQL、调用工具、甚至自己写程序调试自己。

问题来了：**这些代码是 AI 生成的，你不完全信任它。**

而普通容器（runc）的隔离其实很弱：

| 弱在哪 | 后果 |
| --- | --- |
| 共享**节点**内核（宿主 = Node，不是 Pod） | 一个内核漏洞的利用就能从容器逃到节点 |
| 默认以 root 跑 | 容器内 root 是「有能力的 root」 |
| 挂载与设备访问 | 配错一个 `hostPath` 就是灾难 |
| 内核版本与节点一致 | 节点内核的 CVE 直接影响该节点上的所有容器 |

2019 年 CVE-2019-5736（runc 逃逸）就是个经典例子：容器里能拿到**节点上**的 runc 二进制，改掉它，等节点再次执行就拿到了节点权限。

**结论**：让 AI 在你的正式集群里随便跑代码，等于把 root 密码给它。需要更硬的隔离。

## 二、普通容器到底隔离了什么

先理解容器是什么：

```
应用进程 A            应用进程 B
    │                    │
┌───▼────────────────────▼───┐
│  Namespace（命名空间隔离）    │  ← 看不到对方的进程/网络/文件
│  Cgroups（资源限制）         │  ← 限制 CPU/内存
│  Capabilities（权限裁剪）    │  ← 去掉部分 root 能力
└───────────┬────────────────┘
            │ 系统调用（syscall）
            ▼
┌───────────────────────────────┐
│   共享的节点 Linux 内核（宿主） │  ← 关键：这个节点上所有容器共用它
└───────────────────────────────┘
```

**Namespace 只隔离「视图」，不隔离「内核」。** 所有容器最终都在同一个内核上执行 syscall，内核是唯一的共享边界。

### 2.1 「宿主」到底指什么：Node，不是 Pod

这一点很容易搞混，必须先说清楚：

> **「宿主」= Node（节点）及其操作系统内核。Pod 没有内核。**

内核属于操作系统，操作系统装在**节点**上。Pod 只是节点上「一组共享网络命名空间的进程」，是个逻辑概念，并没有自己的内核。

```
┌─────────────────────────────────────────────┐
│ Node（节点 / 宿主机）                          │
│  · 一个操作系统，**一个内核**                    │
│  · 上面跑 kubelet、containerd、kube-proxy      │
│                                              │
│  ┌──────────────┐  ┌──────────────┐          │
│  │ Pod A        │  │ Pod B        │          │
│  │ ┌──────────┐ │  │ ┌──────────┐ │          │
│  │ │ 容器 app │ │  │ │ 容器 app │ │          │
│  │ └──────────┘ │  │ └──────────┘ │          │
│  └──────────────┘  └──────────────┘          │
│       ↓ 系统调用         ↓ 系统调用            │
│  ═══════════════════════════════════════════  │
│      全都进这个节点的内核（只有一份）           │
└─────────────────────────────────────────────┘
```

**所以「谁和谁共享内核」要分情况说**：

| 对比对象 | 是否共享内核 | 说明 |
| --- | --- | --- |
| 同一个节点上的 Pod A 和 Pod B | ✅ 共享 | 用的是这个**节点**的内核 |
| 同一节点上的容器与宿主进程 | ✅ 共享 | 同一份内核 |
| 同一 Pod 内的多个容器 | ✅ 共享 | 而且共享得更多（网络、IPC、卷） |
| **跨节点的两个 Pod** | ❌ **不共享** | 各自用自己节点的内核 |

**推论**：节点 1 的内核出漏洞，只影响**节点 1 上的所有 Pod**，节点 2 不受影响。
**所以真正的资源与安全边界是 Node，不是 Pod。**

### 2.2 「共享」是在 syscall 层面，不是「互相看得见」

容器 A 和容器 B 共享内核，但**互不可见**：

| 隔离的东西 | 机制 | 效果 |
| --- | --- | --- |
| 进程 | PID namespace | A 看不到 B 的进程 |
| 网络 | Network namespace | 各自独立 IP、端口表 |
| 文件系统 | Mount namespace | 各自独立的 rootfs |
| 主机名 | UTS namespace | 各自 hostname |
| CPU/内存 | Cgroups | 各有限额 |

容器 A 调用 `open()` 时，**执行它的是节点内核**，只是内核会按 A 的 mount namespace 决定看哪个文件系统。

> **准确表述：syscall 层面共享节点内核，视图层面各自隔离。**

### 2.3 怎么亲眼验证

在 Pod 里和节点上分别看内核版本：

```bash
# Pod 里
kubectl exec <pod> -- uname -r

# 节点上
kubectl debug node/<node> -it --image=busybox -- uname -r
```

| 运行时 | Pod 里的 `uname -r` |
| --- | --- |
| **runc** | **与节点完全相同**（同一个内核） |
| gVisor | 假版本号（如 `4.4.0`），与节点不同 |
| Kata | guest 内核版本，与节点不同 |

「runc 下两者完全一样」就是共享内核最直观的证据。

### 2.4 三种运行时在这件事上的差别

| | 容器的 syscall 进到哪 |
| --- | --- |
| **runc** | 直接进**节点内核** |
| **gVisor** | 先进 **Sentry（用户态假内核）**，只向节点内核发极少量受控请求 |
| **Kata** | 进**自己 Pod 的 guest 内核**，不碰节点内核 |

所以「共享内核」这个说法**只对 runc 完全成立**：gVisor 是「名义上共享、暴露面大幅收窄」，Kata 是「根本不共享」。

---

所以要更安全，只有两条路：
- **不让它直接碰真内核** → gVisor（拦截 syscall，自己模拟一个内核）
- **给每个 Pod 一个独立的内核** → Kata（用轻量虚拟机）

## 三、gVisor：用「假内核」挡住真内核

### 3.1 原理

```
     应用
      │ syscall
      ▼
┌──────────────────────────┐
│  Sentry（用户态内核）      │  ← gVisor 用 Go 写的「假内核」
│  · 自己实现 syscall 语义   │
│  · 管理内存、文件、网络     │
└───────────┬──────────────┘
            │ 少量且受控的 syscall
            ▼
┌──────────────────────────┐
│  节点真内核（宿主机内核）   │
└──────────────────────────┘
```

关键点：
- 应用的 syscall **不直接进真内核**，而是进 gVisor 的 **Sentry**（一个运行在用户态的进程）。
- Sentry 是真正的内核模拟器，它自己处理文件系统、内存管理、网络协议栈。
- Sentry 只对真内核发起**极少量、经过严格审查**的 syscall。
- 还有一种模式 `ptrace`/`KVM` 平台：可以在 KVM 上跑 Sentry，性能更好。

**类比**：普通容器是「在别人家借住一间房」，gVisor 是「你有一间房，但墙、水电、门锁都是你自己装的，外面的房东根本进不来」。

### 3.2 性能与代价

| 优点 | 代价 |
| --- | --- |
| 隔离强，内核攻击面大幅缩小 | syscall 兼容性不完整，部分程序跑不起来 |
| 不需要硬件虚拟化 | 系统调用密集型应用有性能损失（IO、网络） |
| 启动快（仍是进程） | GPU 支持有限（重要！见下文） |

**实测经验**：Web 服务、Python/Node 脚本通常性能损失 10–30%；高 IO 场景可能更明显。

### 3.3 在 K8s 里怎么用

K8s 通过 **RuntimeClass** 让你选择运行时：

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc                # gVisor 的 containerd shim 名
---
apiVersion: v1
kind: Pod
metadata:
  name: untrusted-code
spec:
  runtimeClassName: gvisor    # ← 关键：这个 Pod 用 gVisor 跑
  containers:
    - name: runner
      image: python:3.12-slim
      command: ["python", "-c", "print('hello')"]
```

**原理**：kubelet 看到 `runtimeClassName`，告诉 containerd 用 `runsc` 这个 CRI handler 创建容器，而不是默认的 `runc`。

前提：节点上装好 gVisor 与 containerd 配置（或直接用 GKE 的 Sandbox 节点池）。

### 3.4 常见坑

- **没有 GPU 直通**：gVisor 对 CUDA 支持很差，不能用来跑模型推理；但**可以用来跑 Agent 的工具执行环境**（CPU 沙箱）。
- **兼容性**：某些依赖内核特性的程序会失败（如 `io_uring`、特定 `ioctl`）。
- **调试困难**：`kubectl exec` 体验正常，但底层日志和 `/proc` 行为有差异。

## 四、Kata Containers：给每个 Pod 一个独立内核

> 严格说是「给每个 **Pod** 一个 guest 内核」：同一个 Kata Pod 内的多个容器仍共享那个 guest 内核；它隔离的是**节点内核**。

### 4.1 原理

```
     应用
      │ syscall
      ▼
┌──────────────────────────┐
│  容器根文件系统（rootfs）  │
├──────────────────────────┤
│  轻量虚拟机内核（guest）   │  ← 每个 Pod 一个独立内核
└───────────┬──────────────┘
            │
┌───────────▼──────────────┐
│  VMM（QEMU/Cloud Hypervisor/Firecracker）│
└───────────┬──────────────┘
            │ 硬件虚拟化（KVM）
            ▼
┌──────────────────────────┐
│  节点（Node）及其内核        │
└──────────────────────────┘
```

关键点：
- 用**硬件虚拟化**给每个 Pod 起一个微型 VM。
- 容器在 VM 里跑，用的是 **guest 内核**，与**节点内核**完全隔离（注意：是节点内核，不是 Pod 的）。
- 兼容性几乎与普通容器一致（因为跑的是真 Linux 内核）。

**类比**：普通容器是「合租」，gVisor 是「自己装修」，Kata 是「整租一套房，有自己的水电系统」。

### 4.2 性能与代价

| 优点 | 代价 |
| --- | --- |
| 兼容性最好（真内核） | 需要硬件虚拟化（裸金属/云上支持嵌套虚拟化） |
| 隔离强（VM 级） | 内存开销更大（每个 VM 有内核开销） |
| 可搭配 GPU 直通（部分方案） | 启动比 gVisor 慢一些 |

### 4.3 在 K8s 里怎么用

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kata
handler: kata-qemu
---
apiVersion: v1
kind: Pod
spec:
  runtimeClassName: kata
```

同样通过 RuntimeClass 切换。云厂商、OpenShift 都有较成熟的 Kata 支持。

## 五、三者对比：runc / gVisor / Kata

先把三种运行时放在一起看，注意**隔离的对象是「节点内核」，不是 Pod**：

| 维度 | runc | gVisor | Kata Containers |
| --- | --- | --- | --- |
| **隔离机制** | Namespace + Cgroups | 用户态内核（Sentry）拦截 syscall | 轻量 VM + 独立内核 |
| **容器的 syscall 进到哪** | 直接进**节点内核** | 先进 Sentry，再少量转发节点内核 | 进**自己 Pod 的 guest 内核** |
| **是否与节点共享内核** | ✅ 完全共享 | ⚠️ 名义共享，暴露面大幅收窄 | ❌ 不共享 |
| 隔离强度 | 弱 | 强 | 很强 |
| 兼容性 | 100% | 中（部分 syscall 未实现） | 高（真内核） |
| 性能 | 基准 | 下降（syscall 密集型明显） | 接近原生，略慢 |
| 启动速度 | 最快 | 快（用户态进程） | 慢（要起 VM） |
| 资源开销 | 最低 | 低 | 中（每个 Pod 一份 VM 开销，需配 RuntimeClass 的 `overhead`） |
| GPU 支持 | 好 | 差（不可直通） | 部分方案支持 |
| 依赖 | 无 | 无特殊硬件 | **需要 KVM** |
| Pod 内 `uname -r` 看到 | **与节点完全相同** | 假版本号 | guest 内核版本 |
| 典型用途 | 自家可信业务 | Agent 跑不可信代码 | 多租户强隔离、需要内核兼容 |

**怎么选**：

```
你要跑什么？
│
├─ 自家可信的业务代码 ──────────▶ runc（性能最好，最简单）
│
├─ AI 生成的、不可信的代码
│   ├─ 要快、够用就行 ──────────▶ gVisor ✅
│   └─ 要完整内核兼容 + 最强隔离 ─▶ Kata
│
├─ 多租户 SaaS，客户代码互相隔离 ─▶ Kata（或云厂商 MicroVM）
│
└─ 需要 GPU 的推理/训练 ────────▶ runc（或 Kata + GPU 直通，视方案）
```

**注意它不是二选一**：同一个集群里可以让主业务用 runc、Agent 沙箱用 gVisor，通过 **RuntimeClass** 按 Pod 分别指定。

### 5.1 单看 gVisor 与 Kata 的取舍

| 维度 | gVisor | Kata Containers |
| --- | --- | --- |
| 隔离机制 | 用户态内核拦截 syscall | 轻量 VM + 独立内核 |
| 隔离强度 | 强 | 很强 |
| 兼容性 | 中（部分 syscall 不支持） | 高（真内核） |
| 启动速度 | 快 | 中 |
| 资源开销 | 低（进程） | 中（VM 内存开销） |
| GPU 支持 | 差 | 某些方案支持 |
| 依赖 | 无特殊硬件要求 | 需要 KVM |
| 适用 | Agent 跑脚本/工具、不可信代码 | 需要完整内核兼容 + 强隔离、多租户 |

**给 Agent 场景的建议**：
- **工具执行 / 代码沙箱** → gVisor（轻、快、够用）
- **需要 GPU 或多租户强隔离** → Kata（或云厂商的 MicroVM 方案）

## 七、小白容易混淆的点

| 混淆 | 澄清 |
| --- | --- |
| **容器就是虚拟机吗？** | 不是。容器是节点上的进程 + 隔离，与**节点内核**共享 |
| **gVisor 是虚拟机吗？** | 不是，它只是一个用户态进程，用 syscall 拦截模拟内核 |
| **Kata 是容器吗？** | 对用户来说还是容器（镜像、Pod 语义不变），但底层是 VM |
| **用了 gVisor 就不用管权限了吗？** | 不是。仍要非 root、只读根文件系统、最小 capabilities |
| **隔离越强越好吗？** | 不是，要在兼容性、性能、成本之间取舍 |
| **RuntimeClass 只能选运行时吗？** | 它还可以带 `overhead`（调度时预留额外资源）和 `scheduling`（节点选择），对 VM 型运行时很有用 |

## 八、面试会怎么问

**Q1：为什么 AI Agent 需要更强的隔离？**
因为 Agent 执行的是模型生成的不可信代码，普通容器共享内核，逃逸风险高。

**Q2：gVisor 的原理？**
在用户态实现内核（Sentry），拦截应用 syscall 并自行处理，只向真内核发起少量受控调用。

**Q3：Kata 的原理？**
用轻量 VM 提供独立 guest 内核，容器运行在 VM 内，通过硬件虚拟化与**节点内核**隔离。

**Q4：如何在 K8s 中启用？**
安装运行时 + 配置 containerd handler + 创建 RuntimeClass + Pod 指定 `runtimeClassName`。

**Q5：为什么 gVisor 不适合跑 GPU 推理？**
它不直通 GPU 设备与驱动，CUDA 依赖的内核接口无法支持；GPU 推理用普通运行时或 Kata + GPU 直通。
